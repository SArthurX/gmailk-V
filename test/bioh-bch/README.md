# BCH Quantitative Analysis Simulation

本程式用於模擬並計算 BioHash 演算法中最佳的 BCH 容錯力（ $t$ 值），確保系統具備最高的安全性（FAR = 0）與最佳的體驗（極低的 FRR）。

## 1. 如何使用真實資料做測試

**執行指令範例**：

```bash
uv run simulate_biohash.py --real_genuine ./my_genuine.npy --real_imposter ./my_imposter.npy
```

_若不加上引數，程式將會預設使用高斯雜訊生成合成數據供您驗證運作邏輯。_

## 2. 關於數據的解釋

- **X 軸（Hamming Distance / 漢明距離）**
  - 代表兩個指紋（511 bits）之間「不一樣的位元數量」。數字越小，代表兩個人臉越像；數字越大，代表差異越大。
- **紅色山峰（路人分佈 / Imposter）**
  - 當我們拿兩個不同人的臉來比對時，因為 511 個位元是隨機且獨立的，機率上會有大約一半的位元相同、一半不同。因此紅色山峰會完美地坐落在 255.5 (也就是 511 的一半) 附近。這證明了我們的演算法沒有偏差（Bias），防偽性極高。
- **藍色山峰（本人分佈 / Genuine）**
  - 這代表同一個人不同角度或光線下的人臉。理想情況下，這座山峰應該要盡量靠近左邊（0 的位置）。
  - （備註：預設的合成數據因為是隨機常態分佈雜訊，所以山峰偏右，換成真實人臉數據後這座山會大幅往左移動。）
- **FAR（錯誤接受率）與 FRR（錯誤拒絕率）**
  - 當我們設定 BCH 容錯力 $t = 30$，意思是在 511 個位元中，只要錯 30 個以內系統都會放行。
  - 如果紅山（路人）有部分面積跑到了 30 以左，那就是 **FAR (把路人當成主人)**，這是嚴重的安全漏洞。
  - 如果藍山（主人）有部分面積跑到了 30 以右，那就是 **FRR (主人解鎖失敗)**，這會影響使用者體驗。

## 3. 如何判斷最佳的 t 值 (EER)?

$t$ 值的判斷**不是指把紅山跟藍山分得最開的距離**，而是指**兩座山的交界處，讓 FAR 與 FRR 達到最佳平衡（交會）的那條垂直線**。

更精確地說，在門禁或生物辨識系統中，我們通常要求 **FAR 必須為 0**（絕對不允許路人解鎖）。
因此，我們要在終端機印出的評估表格中，找到一個 $t$ 值滿足：

1. **FAR = 0.00%** （確保安全性）。
2. 在所有滿足條件 1 的 $t$ 中，挑選讓 **FRR 最低** 的那個值。這就是您的系統應該寫進 C++ 原始碼的最佳容錯參數！

## 4. 模擬與實際 C++ 程式運作會有落差嗎？

**在數學上，它們是 100% 完全相等的。**

Python 的 `np.dot` 執行的高維度矩陣相乘，與 C++ 中實作的浮點數乘加運算是完全一致的。中位數的計算與排序（Sorting）也是確定性（Deterministic）的演算法。

**唯一的微小差異在於「浮點數精度 (Floating Point Precision)」**：
Python 預設使用 64-bit 雙精度 (`float64`)，而 CV181X 的硬體與 C++ 通常使用 32-bit 單精度 (`float32`)。為了消除這個落差，我已經在載入真實資料的 `load_real_data` 函式中，**強制將 numpy 陣列轉型為 `np.float32`**。
因此，這套 Python 模擬器跑出來的 511 bits 結果，會跟您設備上的 C++ 跑出來的結果 **完全一模一樣（Bit-exact）**。

## 5. 獨立特徵擷取工具 (C++ Standalone Extractor)

為了方便在 CV181X 設備上自動批次擷取人臉特徵，我們在 `tools/extract_features/` 實作了獨立的 C++ 擷取工具。

### 特色

- **不依賴攝影機 (No VI binding)**：只初始化 CV181X 的影片記憶體池 (VB Pool) 和系統核心 (SYS)，可以直接跑在靜態圖片上，不會產生硬體資源衝突。
- **輸出為 JSON**：所有的檔名與 512 維度浮點數會直接被存成 JSON 檔案，完美無縫銜接 `simulate_biohash.py` 分析。

### 編譯與使用

```bash
cd tools/extract_features
source ../../build/envsetup.sh  # 或回到根目錄執行 source envsetup.sh 再進來
make

# 執行指令：./extract_features <scrfd> <arcface> <image_folder> <output.json>
./extract_features /mnt/data/models/scrfd.cvimodel /mnt/data/models/arcface.cvimodel /mnt/data/genuine_photos /mnt/data/genuine.json
```

## 6. 量化測試與角度分析報告

我們針對 **BF16 (高精度)** 與 **INT8 (NPU 加速格式)** 模型，以及 **正臉** 與 **多角度** 拍攝場景進行了定量對比。

### 數據對比摘要 (本人漢明距離)

| 測試場景            | 模型精度 | 平均距離 (Mean) | 最大距離 (Max) | 最佳 $t$ (FAR=0) |
| :------------------ | :------- | :-------------- | :------------- | :--------------- |
| **正臉 (Front)**    | **BF16** | 1.40            | 5              | 5                |
| **正臉 (Front)**    | **INT8** | 3.40            | 14             | 15               |
| **多角度 (Angles)** | **BF16** | 78.80           | 124            | 125              |
| **多角度 (Angles)** | **INT8** | 82.40           | 137            | 140              |

### 核心結論

1.  **量化損失極低**：從 BF16 轉為 INT8，漢明距離僅增加約 **2 ~ 4 bits**。這證明在 Milk-V Duo 上使用 INT8 NPU 加速是極其安全的，精度損失完全在 BCH 的容錯範圍內。
2.  **角度是穩定性的最大殺手**：
    - 正臉拍攝時，BioHash 極度穩定 ($Max=14$)。
    - 多角度拍攝時，BioHash 波動劇烈 ($Max=137$)，遠超 BCH 安全容量 ($t \le 42$)。

### 部署 (C++ 實作參數)

- **模型選擇**：推薦使用 **INT8** 格式以獲得最佳推理效能。
- **BCH 糾錯值 ($t$)**：為考慮真實場景下的極限狀況，設定 **$t = 42$**（在int8下正臉測試結果為 Max 14，取3倍容錯）。
  - 這能完美涵蓋正臉模式下的所有波動 (Max 14)，並留有約 28 bits 的環境容錯空間。
  - 此時 **FAR 依然為 0.00%**，安全性無虞。
  - 此參數可產生 **192-bit (24 bytes)** 的穩定金鑰，符合加密規範。

> [!WARNING]
> 此設定值為個人測試結果，並不適用於每種人臉特徵，請務必重新測試並調整。
